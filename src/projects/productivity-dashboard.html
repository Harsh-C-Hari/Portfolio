02

A deadline is not the same as urgency.

A task due in ten hours with fifteen minutes of work left is fine. A task due in ten hours with eight hours of work left is not. So urgency here blends three signals: time remaining, effort still outstanding, and how those two compare.

remaining_effort = estimated_effort_hours * (1 - progress / 100)
time_pressure = remaining_effort / max(remaining_hours, 0.5)

if time_pressure >= 0.7 or remaining_days <= 1: return "critical"
if time_pressure >= 0.4 or remaining_days <= 3: return "high"
if time_pressure >= 0.15 or remaining_days <= 7: return "medium"
return "low"

How it plays out

Due inEffort leftPressureResult
10 hours8 h0.80Critical
2 days6 h0.13High
5 days2 h0.02Medium
12 days3 h0.01Low

Overdue tasks are critical. Finished tasks have no urgency. With no deadline, 8 or more hours of work left counts as medium, otherwise low.

03

Built like other people will use it.

  • Passwords are hashed with bcrypt.
  • Sessions use an access token plus a refresh token. Refresh tokens are stored only as SHA-256 hashes and rotated on use, and sessions are tracked per device.
  • Roles and permissions work at project level: members, invitations, roles and permissions are separate screens, with a danger zone for destructive actions.
  • Push endpoints are checked so the server's outbound notification requests cannot be pointed at internal addresses.
04

Notifications that do not need the tab open.

The app is an installable PWA with a service worker and Web Push (VAPID). Deadline alerts are sent by the server, so they arrive even when the app is closed.

A few details that mattered:

  • Push messages carry a 6 hour time-to-live, so a phone in doze mode still receives them when it wakes.
  • The server de-duplicates sends, so overlapping triggers cannot double-notify.
  • Nothing inside the app schedules these. A secret-protected dispatch endpoint is pinged on a schedule by an uptime monitor, with a GitHub Actions cron as a backup.
  • That same ping also touches the database, which keeps the free-tier Postgres from going idle.
05

No servers to babysit.

The backend runs as serverless functions on Vercel with PostgreSQL on Supabase. That shaped three decisions:

  • No long-lived connections. Database connections are not pooled inside the app (NullPool); the app talks to the provider's pooled connection string instead.
  • No local disk. Uploads go to object storage, not the function's filesystem.
  • No background workers. Scheduled work is driven by pings, not by a process that stays running.
